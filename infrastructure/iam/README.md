# AEROPIX — IAM setup (least privilege)

The EC2 instance must **never** contain long-lived AWS access keys. Instead,
attach an IAM role to the instance through an instance profile. Boto3 picks the
role credentials up automatically through its default credential chain.

## 1. Replace the bucket placeholder

Edit `aeropix-s3-policy.json` and replace both occurrences of
`REPLACE-WITH-YOUR-BUCKET` with your real bucket name, for example
`aeropix-images-2026-123456789012-ap-south-1`.

## 2. Create the role and instance profile (AWS CLI)

```bash
aws iam create-role \
  --role-name AEROPIX-EC2-S3-Role \
  --assume-role-policy-document file://ec2-trust-policy.json

aws iam put-role-policy \
  --role-name AEROPIX-EC2-S3-Role \
  --policy-name AEROPIX-S3-Least-Privilege \
  --policy-document file://aeropix-s3-policy.json

aws iam create-instance-profile \
  --instance-profile-name AEROPIX-EC2-Instance-Profile

aws iam add-role-to-instance-profile \
  --instance-profile-name AEROPIX-EC2-Instance-Profile \
  --role-name AEROPIX-EC2-S3-Role

# Attach the profile when launching EC2 (or replace an existing profile)
aws ec2 associate-iam-instance-profile \
  --instance-id i-REPLACE-WITH-INSTANCE-ID \
  --iam-instance-profile Name=AEROPIX-EC2-Instance-Profile
```

## 3. Verify from the instance

```bash
# On the EC2 host, with no AWS_* key variables exported:
curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Expected: AEROPIX-EC2-S3-Role

aws sts get-caller-identity
# Expected: the assumed role ARN, not a personal IAM user
```

## Why these permissions?

| Permission | Why it is needed |
|---|---|
| `s3:ListBucket` | `head_bucket` health check and the S3 status panel |
| `s3:GetBucketLocation` | Confirms the bucket region |
| `s3:GetObject` | Reads objects for thumbnails or downloads if needed |
| `s3:PutObject` | Uploads originals and thumbnails with `AES256` |
| `s3:DeleteObject` | Deletes image objects when the user deletes an image |

No `s3:*`, no access to other buckets, no IAM, no EC2, no KMS permissions.
SSE-S3 (`AES256`) is used, so no KMS key policy is required. If you later switch
to SSE-KMS, add a narrowly scoped `kms:GenerateDataKey` / `kms:Decrypt` policy
for that single key.

## Bucket configuration

```text
Block all public access ............ ON (all four settings)
Bucket versioning .................. optional (recommended for recovery)
Default encryption ................. SSE-S3 (AES256)
Static website hosting ............. OFF
Object ownership ................... Bucket owner enforced
```

The application never calls `put_bucket_acl` or `put_object_acl`. All browser
access uses short-lived presigned GET URLs generated by the backend.
